# API 연동 개발·장애 검토 기록

기록일: 2026-10-31, 한국시간(UTC+9)  
대상: 쿠팡 마켓플레이스·로켓그로스, 네이버 주문 조회 및 매출 집계

## 1. 이 문서를 읽는 기준

이 기록은 사용자가 제공한 실제 응답·화면, 저장소 코드 검토, 자동 테스트를 구분한다. 모의 응답 테스트 통과는 실제 쿠팡·네이버 서버의 동작 보장을 의미하지 않는다. 개발 환경에는 운영 API 인증정보가 없어 이번 점검에서 운영 API를 직접 호출하지 않았다.

원본 API 응답의 결제시각·수량과 앱의 한국시간 날짜·환산 수량을 분리해서 확인한다. 비밀키·비밀번호·인증 헤더는 기록하지 않는다. 사용자가 제공한 전체 주문 응답이나 원본 파일도 저장소에 추가하지 않는다.

## 3. 공통 조회 처리에서 지킨 조건

### 최신 조회와 저장 데이터 재사용

- ‘최신 데이터 다시 받기’는 공통 저장 데이터의 완료 구간과 메모리 응답 캐시를 건너뛰고 요청한다.
- ‘저장된 조회 데이터 재사용’은 완료로 기록된 구간을 다시 요청하지 않을 수 있다. 과거에 빈 응답을 정상 완료로 저장했다면 이후 추가된 주문이 자동으로 보인다고 가정하면 안 된다.
- 날짜 처리 규칙을 바꾸면 행 보정만으로 부족하다. 이전 규칙의 완료 구간도 무효화해야 한다.
- 조회 실패·취소 시 미완료 응답을 완료 데이터로 교체하지 않는다. 별도 단계가 이미 완료·저장된 경우 그 단계의 결과는 남을 수 있다.

### 페이지 처리와 중복

- 쿠팡 목록은 `nextToken`이 없어질 때까지 조회한다.
- 같은 페이지 토큰이 반복되면 중단하고 오류를 표시한다.
- 구간 경계가 겹치는 요청은 같은 원본 주문이 중복 반환될 수 있다. 로켓 수집 결과의 동일 JSON 응답을 제거하고, 공통 저장 시에도 행 ID로 중복 제거한다.
- 주문 수, 상품 행 수, 판매수량은 서로 다른 지표다. 주문 하나에 여러 상품 행이나 복수 수량이 있을 수 있다.

### 네이버 처리

- 날짜 작업 최대 동시 실행 수는 2, 요청 시작 간격은 500ms다. 인증 갱신·재시도에도 요청 간격을 적용한다.
- 최초 토큰 발급은 동시 요청을 하나로 합친다.
- 각 날짜의 모든 페이지를 읽고 상품주문 ID를 기준으로 중복 제거하며, 결과는 날짜 순서로 합친다.
- 서버의 `Retry-After` 정보를 전달하고, 취소 시 대기와 네트워크 요청을 종료한다.
- 실제 운영 환경의 속도 향상 비율은 측정하지 않았다.

## 4. 로켓그로스 어제 주문 누락 검토

### 4.1 사용자 제보와 증거

사용자는 스토어와 비교 기준이 모두 UTC+9라고 확인했다.

스토어 화면의 2026-10-30 판매현황:

| 상품 | 판매수량 | 매출 |
|---|---:|---:|
| 연어와 오리 2.4kg | 3 | 104,700원 |
| 치킨 2.4kg | 3 | 80,700원 |
| 오리 2.4kg | 2 | 54,480원 |
| 소고기와 오리 2.4kg | 1 | 36,900원 |
| 합계 | 9 | 276,780원 |

처음 제공한 붙여넣기 원본은 243상품 행·241주문·판매수량 247개였다. 한국시간 결제 범위는 10월 1일 10:53:45부터 10월 29일 04:29:43까지이며 30일 행은 없었다. 이 파일을 현재 날짜 필터에 넣었을 때 243행 모두 보존됐다. 이것만으로는 실제 API가 무엇을 반환했는지, 요청 기간이 맞았는지, 오래된 캐시였는지 구분할 수 없었다.

그 뒤 사용자가 다른 웹앱에서 받은 실제 응답을 제공했다.

```text
GET /v2/providers/rg_open_api/apis/api/v1/vendors/{vendorId}/rg/orders
paidDateFrom=20261030
paidDateTo=20261031
HTTP 200 / message=SUCCESS / code=200 / nextToken=null
응답 주문 11건
```

결제시각을 한국시간으로 변환한 결과:

| 응답 부분 | 한국시간 결제 범위 | 주문·판매수량 | 매출 |
|---|---|---:|---:|
| 10월 30일 | 11:16:09 ~ 23:46:13 | 10건·10개 | 303,680원 |
| 10월 31일 | 08:50:59 | 1건·1개 | 26,900원 |
| 전체 응답 | 위 두 날짜 | 11건·11개 | 330,580원 |

예: `paidAt=1793371573000`은 UTC 2026-10-30 14:46:13, 한국시간 2026-10-30 23:46:13이다. 13자리 값은 밀리초 타임스탬프이며 날짜를 추측하는 값이 아니다.

이번 응답에는 30일 치킨이 4개로, 앞선 스토어 캡처의 3개보다 1개·26,900원 더 많다. 이 차이는 해결됐다고 처리하지 않는다. 같은 조회 시점의 스토어 값과 주문 상태·반영 기준을 다시 대조해야 한다.

### 4.2 검토 과정에서 정정한 판단

1. 처음에는 스토어와 API의 반영 시점 또는 출고 조건 차이를 가능성으로 제시했다. 공식 제공 조건을 확인한 사실이 아니었다.
2. 다른 앱의 실제 응답이 같은 API에서 30일 주문을 반환하므로, ‘쿠팡이 어제 주문을 제공하지 않는다’는 설명으로 결론 내릴 수 없다.
3. UTC+9가 동일해도 요청 파라미터의 종료 경계를 어떻게 해석하는지는 별도 문제다.
4. 기존 모의 테스트는 API의 종료일을 포함한다고 가정했다. 따라서 테스트 통과만으로 종료일 배타 동작을 배제하지 못했다.
5. 우선 앱의 요청 범위를 보완하고 실제 결과를 확인한 다음, 남은 차이에 대해 쿠팡 문의 여부를 판단한다.

### 4.3 코드에서 발견한 위험과 보완

기존 `rocketKoreaDateRanges`는 한국시간 선택 범위를 UTC 날짜로 넓힌 뒤, 각 구간의 마지막 날짜를 그대로 `paidDateTo`에 넣었다. API가 종료 날짜의 0시 미만만 반환하면 마지막 날짜 주문이 빠질 수 있었다. 하루 조회에서 시작일과 종료일이 같은 요청이나, 월말에 끊긴 짧은 구간도 있었다.

수정한 방식:

- 한국시간 시작일의 UTC 날짜부터 요청한다.
- 각 분할 구간의 종료일을 하루 늘려 요청한다. 마지막 구간뿐 아니라 월말 등 모든 구간에 적용한다.
- 하루 여유분을 포함해 최대 30개 날짜 이내가 되도록 실제 대상 구간을 최대 29일로 분할한다.
- 수신 후 `paidAt`을 한국시간으로 변환해 사용자가 선택한 날짜만 남긴다.
- 구간 중복으로 반환되는 동일 원본 주문을 제거한다.
- 처리 버전을 `utc-to-kst-v1`에서 `utc-to-kst-end-buffer-v2`로 바꿔 이전 로켓 완료 구간을 무효화한다. 기존 행은 유지하고 재조회 대상으로 만든다. 다른 채널의 완료 구간은 유지한다.

예를 들어 한국시간 10월 30일 하루 조회는 UTC 날짜 기준 10월 29일부터 31일까지 여유 있게 요청하고, 결과 중 한국시간 30일만 집계한다.

**확정 범위:** 종료일을 배타적으로 처리하는 모의 서버에서 기존 누락이 재현되며, 수정 후 보존된다. 종료일 포함 서버에서도 선택일 외 주문은 제외된다. **미확정 범위:** 실제 쿠팡의 공식 종료일 계약, 두 웹앱의 같은 시각·같은 인증정보·같은 파라미터 응답 비교는 아직 확인하지 못했다. 따라서 이 변경은 확인된 날짜 경계 위험을 제거한 것이며, 운영 원인을 최종 확정한 것으로 기록하지 않는다.

### 4.4 묶음 수량과 금액 지표의 별도 발견

- 처음 파일의 원본 판매수량은 247개다. 상품명에 2개 묶음이지만 원본 수량 1인 행이 7개 있어, 그 7행을 낱개로 환산하면 254개가 된다. 이는 상품명 기준의 단순 점검이며 실제 가중치 설정이 맞다는 검증은 아니다.
- 원본 단가 합계 6,960,710원과 수량×단가 합계 7,039,650원은 다르다. 원본 표의 단가 SUM을 매출 합계로 비교하면 안 된다.
- 10월 30일 스토어 캡처의 상품들은 모두 1개 상품이므로 그 날짜 차이를 묶음 가중치로 설명하지 않는다.

### 작성 시점 배포 상태

`92eccec`까지 원격 `main` 푸시 성공을 확인했다. 이번 종료일 경계 수정은 로컬 변경과 테스트를 완료했지만, 자동 승인 검토가 해당 수정의 별도 운영 배포 승인 부족을 이유로 `main` 푸시를 거절했다. 따라서 작성 시점에는 **운영 미반영**이다. 실제 Render 배포 완료 여부와 운영 재조회 결과도 아직 확인하지 않았다. 후속 배포 시 이 문서에 결과를 추가한다.

## 8. 후속 배포 및 운영 확인

- 사용자의 배포 승인 후 `75ebaaa`를 원격 `main`에 푸시했다.
- 사용자가 날짜 경계 보완 이후 실제 주문이 정상적으로 불러와진다고 확인했다. 공식 API 종료일 계약까지 확인한 것은 아니다.
- `bc9a343`에서 주문 조회의 저장 원본 JSON 보기·복사를 추가하고 사용자 승인 후 푸시했다.
- 후속 개선: JSON 팝업의 ‘API 호출 정보 보기’에서 최근 조회의 호출 시각(UTC·한국시간), 주소, 파라미터, HTTP 상태, 소요 시간, 응답을 복사할 수 있게 했다. 쿠팡 서버 인증에 실제 사용한 Access Key와 네이버 DB 인증 Client ID는 마스킹 식별값만 응답 헤더로 전달한다. 비밀키·서명·인증 토큰은 기록하지 않는다.
- 호출 기록은 현재 페이지 메모리에만 남긴다. 새 조회를 시작하면 초기화되며, 최근 500회·약 8MB 한도로 보관한다. 오래된 기록을 제거하면 `dropped`로 표시한다. 개별 응답이 크면 본문 생략을 명시한다. 저장 데이터 재사용은 API 호출로 꾸며 기록하지 않는다.
- 모든 모달에 바깥 클릭 닫기를 공통 적용했다. 내부 클릭·내부에서 시작한 드래그는 닫지 않으며 기존 `cancel` 처리를 따른다. 조회 진행 모달은 취소를 요청하고 조회가 종료되면 닫힌다.

## 9. 로켓그로스 음수 취소 수량 처리

사용자는 기존 호출 방식은 유지하고, 음수 수량이 반환될 때 합산만 반영하도록 범위를 확정했다. 추가 제공한 18행도 모두 `salesQuantity: 1`이며 취소수량·취소금액·취소상태 필드는 없었다. 실제 API가 음수 취소 행을 반환한다는 사실이나 별도 취소 API는 이번 자료로 확인하지 못했다.

- 기존 경로·조회 날짜 생성·페이지 처리·상세 조회 방식은 유지한다. 취소 전용 호출이나 전체 주문의 추가 상세 호출은 넣지 않는다.
- `salesQuantity`가 음수면 그대로 보존한다. `salesAmount`가 있으면 원본 부호대로 사용하고, 없으면 수량×양수 단가로 음수 매출을 계산한다. 수량과 금액의 부호가 충돌하면 자동 보정하지 않고 오류로 처리한다.
- 주문 원본 상품 집계·대시보드·주간/월간 집계는 부호를 유지해 합산한다. 예: 판매 3개·300원, 취소 -1개·-100원 → 2개·200원.
- 상품명·판매 차이로 취소를 추정하지 않는다. 별도 양수 취소 필드를 임의 차감하거나 이미 음수인 수량에서 다시 취소를 빼지 않는다.
- 공통 저장 원본을 재계산하고 로켓 완료 구간을 무효화해 이전 빈 결과도 재조회할 수 있게 한다.
- ERP API 음수 수량은 기존 로켓 엑셀의 음수 출고 LOT 규칙으로 처리하며 재고를 늘리거나 이번 배부에 재사용하지 않는다.
- 전체 207개 테스트와 브라우저 모의 응답 검사로 검증했다. 실제 음수 취소 응답은 아직 확보하지 못했으며 운영 배포 전 변경이다.
